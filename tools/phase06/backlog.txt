reqs: FR-ACC-08
p04: US-26

api: GET /sanctum/csrf-cookie; POST /api/v1/auth/register
tables: users
ac: Functional | Given a visitor without an account, when they submit first name, e-mail, password, confirmation, the adult confirmation and the terms acceptance, then the API answers 201 with the User and a session starts (AC-FR-ACC-08-2).

ac: Error | Given no valid CSRF token, then 419 `csrf_token_mismatch`; given too many attempts, then 429 with `Retry-After`.
ac: Authorization | Given a visitor who already has a session, then `/register` is not offered (guest-only route) and the endpoint refuses the request.

bt: Feature tests: success, duplicate e-mail, unaccepted checkboxes, missing CSRF, throttling
fe: `/register` page in `AuthLayout`; native HTML validation plus server error mapping (frontend-architecture §11)
fe: RTK Query `register` mutation; on success, set the auth state from the response
ft: Tests for field error mapping and the guest-only redirect

@US-002 | E01 | Log in and log out with a protected session
role: member
want: to log in with my credentials and log out again
so: my account and cart are reachable only through my own session
pri: Must
status: Needs Clarification
qs: Q-40, Q-63
deps: US-001
reqs: FR-ACC-08, NFR-SEC-01, NFR-SEC-02
p04: new (part of US-26)
cls: MVP
sprint: 1
api: GET /sanctum/csrf-cookie; POST /api/v1/auth/login; POST /api/v1/auth/logout; GET /api/v1/me
tables: users, sessions
ac: Functional | Given valid credentials, when the member logs in, then 200 with the User, the session ID is regenerated and `GET /me` returns the member.
ac: Error | Given an unknown e-mail or a wrong password, then 422 `invalid_credentials` with the same message in both cases (no account enumeration).
ac: Error | Given repeated failures for the same e-mail and IP, then 429 `rate_limited` with `Retry-After`.
ac: Functional | Given a logged-in member, when they log out, then 204, the session is invalidated and the CSRF token rotated; a later `GET /me` answers 401.
ac: Security | Given any state-changing request without a valid `X-XSRF-TOKEN`, then it is rejected with 419 (AC-NFR-SEC-02-1).
ac: Security | Given any API request for member data, then no member identifier appears in the URL and the response depends only on the session (AC-NFR-SEC-01-1).
ac: Functional | Given a 401 on a member call, then the SPA clears its auth state, sends the member to `/login?redirect=` and returns them there after login.
be: `SessionController` (login, logout), `LoginRequest` throttled per e-mail and IP, `CurrentUserController`
be: Session and cookie settings per authentication-design §4 (HttpOnly, Secure, SameSite=Lax); lifetime read from config, value pending Q-63
bt: Tests: login success, generic failure, throttling, logout invalidation; 419 on every unsafe route (route-list driven); architecture test that no route takes a user ID parameter
fe: API client base query: CSRF cookie bootstrap, refresh and retry once on 419, redirect on 401 (frontend-architecture §8)
fe: `/login` page; auth state loaded from `GET /me` at start-up
ft: Tests for the single 419 retry and the 401 redirect with return path
inf: Database session driver (baseline); env variables for session lifetime and secure cookies
